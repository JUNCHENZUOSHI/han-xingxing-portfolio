# Design System & DesignOps 系统建设

围绕跨境电商 SaaS 的多产品、多语言与持续迭代需求，从 0 到 1 建立公司级 B 端设计系统。项目覆盖 Design Token、基础组件、业务组件与 DesignOps 治理机制，并以模板站作为重点落地场景，验证系统在真实业务中的复用能力与国际化适配能力。

## 项目背景

### 项目起因

随着跨境业务持续扩展，模板站、广告平台与商家后台逐步进入多产品线并行迭代阶段。原有以单页面、单业务需求为单位的设计方式开始暴露规模化问题。

不同产品线分别维护 UI，同类组件存在多套视觉与交互实现；设计与研发需要反复确认基础样式和组件状态；多语言版本仍依赖页面级人工适配；模板站还要同时处理品牌表达、内容差异与转化效率。

项目初期对现有产品界面与组件资产进行盘点后，我把问题归到四个方向：规则来源不统一、组件重复、国际化依赖页面级修补，以及组件缺少持续治理。项目由页面级优化转向系统建设，目标是建立稳定的设计基线、可复用组件资产与持续维护机制。

### 目标用户

**直接使用者**

产品经理、设计师与前端研发。他们需要明确的设计规则、可复用组件和稳定的协作方式，减少重复设计、重复开发与跨团队沟通成本。

**最终用户**

使用平台完成建站与运营的 Shopify 跨境商家。设计系统不会直接呈现在商家面前，但组件一致性、多语言稳定性和产品迭代质量最终都会反映到商家的使用体验中。

### 业务目标

1. 建立统一设计语言，收敛基础视觉、交互状态与高频组件规则；
2. 提高设计与研发复用效率，降低新增页面与业务模块的重复建设成本；
3. 将多语言、多市场需求前置到 Token、组件和内容规则中；
4. 建立组件准入、变更、发布与版本管理机制，让设计系统可以随业务持续维护。

### 设计约束

- 多产品线已经在持续迭代，系统建设需要兼容既有产品实现；
- 基础规则需要保持一致，同时给业务差异保留扩展空间；
- 多语言适配需要处理文本长度、布局空间、信息密度与内容结构变化；
- Shopify Theme 相关场景需要保留主题层的灵活性；
- 组件需要进入新增、变更、发布、扩展与回收的持续治理流程。

## 核心挑战

### 01｜标准化与业务扩展如何共存

规则过少会继续产生新的设计分支；规则过重又会限制业务组件对真实场景的适配。

我需要先定义系统边界：哪些基础规则必须统一，哪些高频能力应该复用，哪些业务差异允许通过扩展机制解决。

### 02｜国际化如何进入系统层

多语言适配会直接影响文本长度、按钮宽度和表格列宽，表单布局、状态提示与信息层级也会随内容变化。

如果这些问题一直留到页面完成后处理，设计与研发会持续做重复调整。国际化需要进入 Token、组件和内容规则，成为系统默认具备的能力。

### 03｜设计系统如何真正进入业务

组件数量只能说明资产规模，无法证明设计系统已经被业务采用。

系统还需要回答几个实际问题：什么时候应该新增组件，已有组件怎样扩展，设计变更如何同步研发，旧资产怎样退出，以及新页面能否优先复用已有能力。

## 设计过程

整个过程围绕四个问题推进：问题从哪里来、问题应该在哪一层解决、设计规则怎样落到组件、落地后用什么结果判断是否有效。

### 阶段 1｜从页面问题追到系统问题

项目初期先盘点现有产品界面与组件资产，没有直接进入组件重绘。

审计重点包括：

- 基础视觉规则是否存在多个来源；
- 同类组件是否出现重复定义；
- 加载、禁用、错误、空状态等交互规则是否一致；
- 多语言场景是否仍依赖页面级人工修补。

盘点后，页面上的视觉差异可以继续追到规则、组件和维护方式。设计范围也随之从单个页面扩展到系统层。

### 阶段 2｜把问题放到对应层级

我将 Design Token 拆成 Foundation、Semantic 与 Component 三层。

**Foundation Token** 管理颜色、字体、间距、圆角、阴影与栅格等基础变量。

**Semantic Token** 将基础变量映射到文本、背景、边框与状态等使用语义。

**Component Token** 把语义规则继续落到按钮、输入框、表格、弹窗等组件及其不同状态。

这套结构把全局样式、业务语义与组件实现分开。后续调整主题、状态或国际化表现时，可以先定位变化发生在哪一层，再判断影响范围。

### 阶段 3｜把规则放进真实业务

模板站被选为重点落地场景。它同时包含品牌表达、商品展示、促销信息、内容模块与转化链路，能够检验组件在真实业务中的稳定性与扩展性。

验证重点包括：

- 同一套组件能否支撑不同模板组合；
- Token 调整后，组件结构是否仍然稳定；
- 多语言内容变化后，布局与信息层级是否成立；
- 新模块加入时，已有组件和模式能否继续复用。

### 阶段 4｜把维护方式纳入系统

组件进入多产品线后，系统开始面对新增、修改与淘汰。

我把组件新增、变更、发布、扩展与回收纳入固定流程，并通过版本记录同步设计与研发，减少 Figma 资产与线上实现长期分叉。

## 解决方案

### 决策 01｜从组件库扩展到完整 Design System

#### 怎么发现问题

资产盘点中，同类 UI 在不同产品线出现多套实现。基础样式需要反复确认，组件的状态、使用方式与研发实现也没有统一来源。

重复工作已经超过“少几个组件”的范围，问题同时存在于设计规则、组件定义和协作方式中。

#### 怎么判断

我把需要统一的内容拆成四层：

- **设计基础**：统一基础视觉变量与语义规则；
- **组件体系**：覆盖基础组件与核心业务组件；
- **模式规范**：沉淀表单、筛选、表格、弹窗与反馈等高频组合；
- **协作机制**：管理组件新增、变更、发布与版本同步。

判断标准很明确：如果一个问题会在多个产品、多个页面反复出现，就优先沉淀到系统层；只属于单一业务的差异，则保留在业务扩展层。

#### 为什么这样设计

完整 Design System 可以同时处理“设计长什么样”“组件怎么用”和“变更怎么维护”。

组件规范也不只记录视觉样式，还需要明确状态、尺寸、响应式、内容约束与使用边界。这样新页面可以先复用已有规则，业务差异再通过扩展能力承接。

只维护 Figma 组件库虽然能解决部分复用问题，但组件状态、研发同步和长期治理仍会继续分叉。

#### 怎么验证

项目最终完成 **60+ 个基础组件与业务组件**的统一，并逐步应用到模板站、广告相关产品与商家后台。

在新增页面与业务模块中，约 **70%** 的界面能力可以直接复用已有组件或模式。这个结果用来判断设计系统是否真正进入日常业务，而不只停留在组件资产层。

### 决策 02｜把国际化能力放进 Token 与组件规则

#### 怎么发现问题

多语言适配过去主要发生在页面完成之后。文本变长时，按钮、表格、卡片与弹窗容易出现空间不足，设计侧需要重复调整布局与内容承载方式。

同一类问题会随着页面和语言数量继续出现，页面级修补很难形成稳定规则。

#### 怎么判断

这类问题具有明显的重复性，我把它们拆到组件和 Token 两个层级处理。

组件负责文本承载、溢出与弹性布局；Token 负责字号、间距和信息密度等可配置变量。业务场景仍保留必要的扩展位置，避免局部差异反过来复制整套组件。

#### 为什么这样设计

具体规则包括：

- 组件优先采用弹性布局，减少固定宽度依赖；
- 为按钮、标签、表格与表单定义文本承载和溢出策略；
- 明确标题、正文与辅助信息在容器中的内容边界；
- 将字号、间距与信息密度纳入 Token 管理；
- 为业务场景保留必要的扩展能力。

这样处理后，多语言变化优先由已有规则吸收，设计师不需要在每个页面重新寻找补丁。

继续按语言逐页调整，短期改动较少，但页面和语言越多，重复成本越高。

#### 怎么验证

项目落地后，国际化相关设计迭代周期缩短约 **30%**。

这个结果对应的是多语言适配前置后的设计迭代效率，用来判断 Token 与组件规则是否减少了重复布局和内容适配工作。

---

### 决策 03｜用模板站验证 Design System

#### 怎么发现问题

系统规则和组件完成后，还缺一个关键判断：这些规则进入真实业务后是否仍然成立。

规范文件能够说明规则已经被定义，但模板组合、内容变化、多语言和转化链路都会给组件带来新的约束。

#### 怎么判断

我选择模板站作为重点验证场景，因为它同时包含视觉表达、内容模块和业务转化链路，能够集中暴露组件的灵活性与稳定性问题。

验证不只看页面是否能够搭出来，还看已有组件是否能继续复用、Token 调整后结构是否稳定，以及多语言内容变化后信息层级是否仍然成立。

#### 为什么这样设计

模板站落地时持续检查四件事：

- 不同模板组合能否继续使用同一套组件；
- Token 调整能否改变视觉表达，同时保持组件结构；
- 多语言内容变化后，布局是否稳定；
- 新模块加入时，已有组件和模式能否覆盖。

相比先完成规范再等待业务逐步接入，这种方式能更早暴露系统边界，也能让组件规则跟着真实业务一起修正。

#### 怎么验证

模板站成为 Design System 的真实业务落地场景，组件复用与多语言适配都在实际页面中持续使用。

项目落地期间，客户首次购买转化率提升 **8%**。Design System 落地与页面体验优化同期推进，因此这个指标用于记录项目期间的业务变化，不把全部增量单独归因于 Design System。

---

### 决策 04｜通过 DesignOps 管理持续变化

#### 怎么发现问题

设计系统进入多产品线后，组件开始持续新增和修改。局部变更可能影响其他业务，旧组件与重复样式也可能继续进入新页面。

如果只维护组件本身，系统规模越大，版本分叉和历史资产累积的问题也会越明显。

#### 怎么判断

组件需要按生命周期管理。我把治理重点放在新增、变更、发布、扩展与回收五个环节，让每次变化都有明确入口。

判断一项需求是否进入系统时，先看现有组件或模式能否覆盖，再决定新增；涉及全局组件的调整则先评估影响范围。

#### 为什么这样设计

**新增**  
先判断现有组件或模式能否覆盖需求，再决定是否新增。

**变更**  
涉及全局组件的调整先评估影响范围，再进入设计与开发。

**发布**  
通过版本记录同步设计与研发侧变更。

**扩展**  
业务差异优先通过组件属性、组合方式或业务组件承接。

**回收**  
逐步下线重复组件与历史样式，减少旧资产继续进入新页面。

这套机制给组件变化增加了固定路径，避免每个团队各自维护一套处理方式。

#### 怎么验证

组件评审、变更管理、版本发布与旧资产回收最终形成固定协作流程，设计系统也逐步进入模板站、广告相关产品与商家后台等业务场景。

这里的验证重点是治理机制是否真正被持续使用。当前材料没有提供单独的治理效率指标，因此不额外给出未经验证的效率提升数字。

## 项目复盘

### 可复用的方法论

**先判断问题应该在哪一层解决**  
Foundation、Semantic、Component 三层结构把基础设计值、业务语义与组件实现分开。主题、状态或业务表达发生变化时，可以先定位层级，再决定调整范围。

**用复用率和业务接入判断系统是否成立**  
组件数量只能说明资产规模。复用率、业务接入范围与治理机制更能说明系统是否进入日常工作。

**把国际化前置到组件与规则层**  
文本承载、布局弹性、信息密度与组件状态在系统层提前处理，可以减少页面完成后的重复修补。

**用真实业务检验系统边界**  
模板站让组件体系同时面对内容变化、品牌表达和转化链路。真实业务能持续使用已有组件和规则，才说明系统具备复用价值。

### 本次项目带来的判断

设计系统的核心价值是降低变化成本。基础规则保持稳定，业务差异有明确扩展位置，设计与研发才能在产品持续变化时继续使用同一套系统。

DesignOps 决定这套系统能否长期运行。组件第一次发布之后，新增、变更、版本同步与旧资产回收仍然需要持续管理。
